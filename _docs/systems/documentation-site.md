# Eire Politic Documentation Site

## Summary

The Eire Politic Documentation Site is the public technical knowledge-base system for repositories, systems, data, runbooks, architecture decisions, High Director documentation, notes, and archived material. It is implemented entirely in `eirepolitic.github.io` and published through GitHub Pages.

This page is the canonical current architecture reference for the documentation website. The former High Director `site-architecture.md` page is retained only as a superseded historical record.

## Current Implementation State

The system is active on `main`. Jekyll renders committed Markdown and site assets, GitHub Actions validates documentation metadata and references, and GitHub Pages builds and deploys the published site after merges.

No application server, database, Lambda function, external search service, or paid search dependency is part of the current system.

## System Boundary

Included:

- `eirepolitic.github.io` repository content and configuration.
- Jekyll collection rendering for `_docs/`.
- Metadata-driven navigation and indexes.
- Client-side documentation search using generated `search-index.json`.
- Documentation validation through GitHub Actions.
- GitHub Pages build and deployment.

Excluded:

- Source systems documented by the site.
- Private credential stores or secret-management systems.
- External application backends.

## Architecture

1. Authors commit Markdown, YAML, HTML, CSS, JavaScript, and assets to a focused feature branch.
2. Pull requests run documentation validation for relevant changes.
3. Approved changes merge into `main`.
4. GitHub Pages invokes the Jekyll build.
5. Jekyll renders the site and generated indexes, including `/search-index.json`.
6. GitHub Pages deploys the static output.
7. Browser JavaScript provides search, on-page navigation, and discovery behavior.

The system has a public trust boundary: anything committed may remain publicly retrievable through repository history even when excluded from generated listings.

## Rendering Model

The current rendering/navigation implementation is repository-local:

- `_layouts/default.html` — global site shell.
- `_layouts/docs.html` — individual technical-document rendering.
- `_layouts/docs-section.html` — section landing pages.
- `_includes/docs-nav.html` — documentation navigation.
- `assets/css/site.css` — primary design system.
- `assets/css/search.css` — search-specific styles.
- `assets/css/indexes.css` — index/discovery styles.
- `assets/js/site.js` — page-navigation and on-page table-of-contents behavior.
- `assets/js/search.js` — browser-side documentation search.

## Navigation and Discovery

Navigation is generated from document metadata and `_data/docs_sections.yml`, not from physical folder names alone.

Discovery surfaces include:

- top-level section navigation and counts;
- section landing pages;
- client-side full-text search;
- repository, technology, document-type, status, and recent-update indexes;
- explicit related-document metadata;
- same-repository relationships where generated by the site;
- recently updated content on the homepage.

This means a file can remain physically under `_docs/high-director/` for URL/link compatibility while being removed from the High Director website section by changing `section` to `archive`.

## Search Architecture

Jekyll generates `/search-index.json` from public documentation in `_docs/`.

Browser search ranks across available document metadata and text, including titles, summaries, repositories, sections, document types, statuses, technologies, tags, and page content. No search API, database, account, or paid search service is required.

## Inputs and Outputs

### Inputs

Committed repository files, primarily Markdown documentation and YAML metadata. Inputs must avoid secrets and conform to repository validation rules.

### Outputs

A public static website, generated documentation indexes, and `/search-index.json` for client-side search.

## Dependencies

Critical dependencies are GitHub repository hosting, GitHub Actions, GitHub Pages, Jekyll, Python, and `PyYAML==6.0.2` for documentation validation.

## Configuration

Primary configuration is stored in `_config.yml`, `_data/docs_sections.yml`, `DOCUMENTATION_STANDARD.md`, and `.github/workflows/validate-documentation.yml`. No secret values are required by the documented build, validation, or publishing path.

## Deployment and Change Management

The verified environment is the public GitHub Pages site built from `main`.

Material changes follow this sequence:

1. Create a focused branch from current `main`.
2. Make the smallest coherent change set.
3. Open a pull request.
4. Confirm documentation validation succeeds.
5. Merge into `main` only after validation succeeds.
6. Identify the merge SHA.
7. Confirm the matching GitHub Pages build/deployment succeeds for that SHA.
8. Verify affected live pages when relevant.

A failed deployment is corrected on a new or updated focused branch and revalidated before merge.

## Operation and Monitoring

Operational evidence comes from pull-request validation checks and GitHub Pages workflow runs. Routine operations, troubleshooting, and publishing procedures are documented in [Documentation Site Operations](/docs/runbooks/documentation-site-operations/).

## Validation

`scripts/validate_docs.py` validates:

- required front matter;
- allowed sections, document types, and statuses;
- date formats;
- archive requirements;
- duplicate permalinks;
- local links/assets;
- explicit related URLs.

Validation also includes:

- GitHub Actions validation on relevant pull requests;
- GitHub Pages build success after merge;
- GitHub Pages deployment success for the intended merge SHA;
- live-page verification when appropriate.

## Failure Modes and Recovery

- Validator failure: correct the referenced metadata or broken link, then rerun validation.
- Jekyll build failure: inspect `_config.yml`, Liquid, front matter, layouts, and the Pages build log.
- Deployment failure after successful build: inspect the deploy job and correct the underlying issue rather than treating build success as deployment success.
- Missing navigation or search content: verify `section`, metadata, visibility, generated indexes, and the latest deployment.
- Incorrect category placement: classify by the page's primary subject, not by the agent/person that authored it.

## Security and Access

The site and repository are public. Credentials, tokens, private keys, session data, secret values, personal data, and confidential identifiers must not be committed.

`visibility` controls generated listings/search behavior only; it is not a security boundary because committed content may remain accessible through repository history.

## Known Limitations

- Availability depends on GitHub Pages and GitHub-hosted infrastructure.
- Search is browser-side and depends on the generated index.
- No separately verified local Jekyll preview procedure is currently part of the operating standard.
- Public URL migrations require care because the current site does not use a redirect plugin; preserving existing permalinks is preferred during category cleanup.
